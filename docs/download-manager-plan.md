# 跨平台下载管理器 · 技术方案

> 定位：主流下载管理器的能力基线 + **编码级可选的视频下载** + **可批量筛选的资源嗅探**；常驻不卡、占用低；Windows / macOS / Linux。
> 状态：方案评审稿 v1.0 · 2026-11-07

**置信度标记说明**
`【已验证】` 有公开文档或事实可核对；`【待验证】` 是本方案的**目标值/估算**，必须在 M0 里程碑用基准测试确认；`【未知】` 当前无法判断，需实验或信息补充。

## 0. 结论速览

1. **技术栈**：Rust 核心 + Tauri 2（系统 WebView）+ React/TS 前端。**不选 Electron**——常驻型工具的 3~4 倍内存与冷启动代价，正好和"不卡"的卖点冲突。【已验证：机制】【待验证：实测数字】
2. **引擎**：Tokio 异步 I/O + **启动即预分配定长文件** + **分段定位写（pwrite）**，不做"下载完再合并临时分片"。这是消灭"完成瞬间卡 2 秒"的关键。【待验证：实测】
3. **内存**：每任务固定上限约 4MB 缓冲 + 全局/每主机连接闸门 + 进度事件 10Hz 合并 → 目标是 1000 任务时整体 RSS < 160MB。【待验证目标】
4. **UI 隔离**：UI 线程零网络、零磁盘、零哈希；进度走差量 + 列表虚拟化；历史分页加载。
5. **视频**：把 **yt-dlp 当 sidecar 子进程**（不是当库），用 `-J` 拿"格式全集"，自己渲染编码/分辨率/码率/HDR/体积矩阵；**能直连的走自家引擎**（保住续传与限速），必须由 yt-dlp 处理的才委派给它。【已验证：yt-dlp 有独立二进制与 `-J` JSON】
6. **嗅探**：默认走"浏览器扩展 + Native Messaging"，**MITM 证书代理默认关闭**，作为白名单化的高级模式；CDP 只作兜底。【待你拍板】
7. **队列**：加权公平调度 + 两级并发闸门 + **分段级**指数退避重试，不是整文件重下。
8. **合规**：只做用户有权下载的内容。**不实现 DRM、付费墙、平台访问控制的绕过**；遇到 Widevine/PlayReady/FairPlay 直接拒绝并说明原因。
9. **浮动条**：能做"只在有视频时出现"，但要分 A/B/C 三档（详见 §5.6）；**真正无解的是 DRM 与私有传输**，工具栏徽标必须做永远准确的兜底。
10. **分发**：不上架商店也装得上——Chromium 走 Edge 加载项商店 + 开发者模式兜底，Firefox 走 AMO unlisted 签名 + 自托管 XPI；**Safari 不进第一版发布范围，仅作开发者本机自测**（详见 §10.4）。

11. **命名**：原名 **Hydra** 与已存在的跨平台下载管理器 **ja7ad/hydra**（Rust · Windows/macOS/Linux + 浏览器扩展 + CLI）重名，需更名；核查后建议 **Fetchweir**（详见 §11）。界面稿已同步替换。

12. **更新器**：常驻"检查更新 / 打开主页"，发现新版本再出现"更新 / 仅下载"，两种方式都支持加速镜像并可手动切换；Pathleap 的更新模块尚标注 M3 未实现，无可复用代码，规格见 §12，已实现状态与实测数据见 §12.6。

**明确不做**：不内置站点白名单式"破解"逻辑、不代管账号 Cookie 云端同步、不做 P2P/吸血、不做"绕过验证码"；**也不做任何 DRM/付费墙/访问控制的绕过，包括不对外发布的私有版本**（理由与法律依据见 §8.1）。

## 1. 产品差异化在哪

| 维度 | 传统下载管理器 | 本产品 |
|---|---|---|
| 通用下载 | 强 | 等价能力 + 现代 UI |
| 视频下载 | 弱/靠站点规则，通常只有"最高画质" | **完整格式矩阵**：分辨率 × 编码 × 帧率 × 容器 × 码率 × HDR，可自由组合，并给**设备/软件兼容性提示** |
| 嗅探 | 弱 | 页面级资源发现 + **媒体族分组** + 批量筛选并入队 |
| 性能 | 常被反馈"卡" | 把"卡"的每个根因写进架构并用指标守住 |
| 跨平台 | 仅 Windows | Win/macOS/Linux 同构 |

真正的差异点是第 2 行：**"我要 1080p 的 H.264，不要 4K 的 AV1，因为我的剪辑软件不吃 AV1"**——这不是"最高画质"能表达的。

## 2. 技术栈选型

### 2.1 候选对比

| 方案 | 空闲内存(估) | 冷启动(估) | 安装包(估) | 渲染一致性 | 原生集成 | 迭代速度 | 判断 |
|---|---|---|---|---|---|---|---|
| **Tauri 2 + Rust** | 60–100MB | 200–500ms | 8–20MB | 中（三平台 WebView 有差异） | 高（Rust 直调 OS API） | 中快 | **选** |
| Electron 30 | 110–180MB（空闲即 3~4 进程） | 800ms–2s | 90–150MB | 高 | 中（要过 IPC 到 Node） | 快 | 不选 |
| Qt6 + QML | 35–60MB | 150–400ms | 25–40MB | 高（自绘） | 最高 | 中 | 备选（团队有 C++ 时） |
| Flutter Desktop | 60–120MB | 400–900ms | 40–70MB | 高 | 中低（平台插件薄） | 中快 | 不选 |
| Rust + egui | 20–40MB | <150ms | 8–15MB | 低（控件原始） | 高 | 慢（UI 全靠手写） | 不选 |

上表内存/启动数字为**公开基准的区间估算**【待验证】，M0 需在同一台机器上把 Tauri 与 Electron 各打一个最小壳实测，作为选型闸门。

### 2.2 结论与理由

选 **Tauri 2**：下载管理器的重活（网络、磁盘、哈希、调度）天然属于 Rust；UI 是一套网页，一套代码三平台。Rust 侧无 GC、无 VM、可精确控制内存，正好对上"常驻低占用"。

**代价要说清楚**：
- 三平台 WebView 不是同一个引擎（Windows WebView2 / macOS WKWebView / Linux WebKitGTK），复杂 CSS（大模糊、多层 backdrop-filter）在 Linux 上会掉帧、偶有渲染差异 → **用"克制"的视觉方案**（纯色/渐变/1px 描边，少用大范围模糊）规避。设计稿已按此约束出。
- 原生观感靠自绘 + 调 OS API（托盘、通知、跳转到 Finder/资源管理器），要写少量平台适配代码。
- Linux 打包（AppImage/Flatpak）与签名链路比 Electron 麻烦。

### 2.3 坦率说 Electron 的代价

如果这个产品是"一年用三次的转换工具"，Electron 完全正确。但它是一个**整天挂在后台**的下载管理器：

1. 空闲就吃 110–180MB 和 3~4 个进程，笔记本上体现为风扇与续航；
2. 冷启动 1 秒级，"点开即用"的工具爽感消失；
3. 包体积 100MB+，自动更新的下载量翻十倍；
4. 架构容易退化成"渲染进程直接读写文件"，这正是同类工具被用户吐槽"卡"的经典成因；
5. 安全面更大（Node 集成 + 远程内容 + 大量依赖）。

**除非**团队完全没有 Rust 能力且交付时间极紧，否则不选。

## 3. "快"和"省"的具体设计

### 3.1 先列"卡"的根因，逐条给对策

| 症状 | 真实根因 | 设计对策 | 怎么验证 |
|---|---|---|---|
| 多任务一开就卡 | 每收到一块数据就发一次进度事件 → IPC/重绘风暴 | 引擎侧合并：单任务 ≤10Hz，全局 ≤30Hz 聚合；UI 侧差量更新 + 列表虚拟化 | rAF 帧时间 p95 < 16ms |
| 下载完成瞬间卡 2–3 秒 | 收尾时把 N 个临时分片**串行合并**并算哈希，且在主线程 | **预分配 + 定位写**，没有合并步骤；哈希放到低优先级阻塞池，不参与收尾动画 | 完成事件 → UI 更新 < 50ms；4GB 校验期间帧率不掉 |
| 内存涨到 GB | 整文件缓存 / mmap 写 / 无界队列 | 每任务固定缓冲上限；有界通道 + 背压；**绝不 mmap 写大文件** | RSS 曲线平顶 |
| 用久了越来越卡 | 历史表全量渲染、SQLite 每条同步写 | 分页 + WAL + 批量提交（1Hz/32MB checkpoint） | 1000 任务下列表滚动帧率 |
| 整机变卡 | 连接数爆炸、fsync 风暴、杀软扫描大文件 | 全局/每主机连接闸门；**不做逐块 fsync**；下载中不反复重命名文件 | 连接数曲线、CPU、磁盘队列 |
| 启动慢 | 启动时做迁移/扫盘/预热 | 首帧优先，迁移与索引维护丢到后台；引擎懒初始化 | 冷启动计时 20 次取 p50/p95 |
| 大文件把机械盘拖死 | 16 条随机写打散在 HDD 上 | 探测介质（`/sys/block/*/queue/rotational`、Windows seek-penalty 查询），HDD 默认降到 4 段 | 吞吐对比测试 |

### 3.2 下载引擎

**文件写盘（核心决策）**
- 开始时 `create` + `set_len(total)`：NTFS/APFS/ext4 上是稀疏分配，瞬间完成，最终大小已知。
- 每个分段独占 `[start, end)`，用**定位写**（Rust `File::write_at` / Windows `WriteFile` 带偏移）写入。没有共享游标、没有锁、没有合并、没有回填。
- 分块读 512KB → 直接落盘，不攒内存。
- **不做逐块 fsync**。只在 checkpoint 时刷（每 2s 或 32MB）；崩溃最多重下最后几 MB，换来的是一条平稳的磁盘队列。
- 结束只做一次顺序校验（可选 SHA256，默认只在用户勾选时执行）。

**并发模型**
- Tokio 多线程运行时，worker 数 `min(物理核, 8)`（不是逻辑核全开——下载是 I/O 密集，线程多了只会抢 CPU）。
- 三级闸门：全局连接上限（默认 32）、每任务连接上限（默认 8，上限 16）、**每主机上限（默认 6，对齐浏览器惯例，避免触发站点限流）**。
- 调度器 100ms 一次 tick，用**赤字轮询（DRR）** 在任务间分配带宽与连接额度，保证"批量任务不饿死前台单任务"。
- 限速用**令牌桶 + 读取延迟**实现，不用 sleep 线程；全局限速与单任务限速分层。

**内存账**
- 每任务 = 分段数 × 512KB 在途缓冲 + 元数据 ≈ **4MB**（8 段）。
- 写入队列有界（每任务 8MB），磁盘慢时反压到网络读取，内存不会顶穿。
- 全局池化缓冲（`bytes::Bytes` 池），避免反复分配。

**吞吐目标**【待验证】：千兆链路、8 段、NVMe 下 ≥ 90% 链路带宽；CPU < 单核 15%。

### 3.3 线程与进程隔离

```
┌───────────────────────────┐        ┌────────────────────────────┐
│  WebView (UI 进程)         │  IPC   │  Rust Core (主进程)          │
│  · 渲染 / 交互 / 虚拟列表   │◄──────►│  · 调度器 / 队列 / 状态机     │
│  · 只消费差量事件           │ 10Hz   │  · 网络 I/O (Tokio)          │
└───────────────────────────┘        │  · 写盘 (定位写)              │
                                     │  · SQLite (独立线程, WAL)     │
                                     │  · 哈希/校验 (低优先级池)      │
                                     │  · yt-dlp 子进程管理          │
                                     └────────────────────────────┘
```

硬规则（写进 CI 检查与 code review checklist）：
1. 网络、磁盘、哈希、ffmpeg 一律不出现在 UI 进程；
2. 跨进程只传**结构化差量**（`{id, done, speed, state}`），不传整表；
3. 任何 >1MB 的字符串（清单、日志）都走分页/截断；
4. UI 刷新以 rAF 为节拍合并，不按事件数量刷新。

### 3.4 启动速度

- 进程启动 → 窗口可见 → 可交互，三段时间分别打点（`Instant` → `tracing` span）。
- 首帧不等待数据库、不等待引擎、不等待扩展握手：先画骨架，再补数据。
- 扩展/Native Messaging 握手放到后台，超时 300ms 就降级为"未连接"。
- 目标：Win 冷启动 TTI p50 < 600ms、p95 < 900ms；热启动 < 300ms；macOS 同量级；Linux 允许 +40%（WebKitGTK 初始化更重）。【待验证目标】

### 3.5 可量化目标与验收方法

| 指标 | 目标 | 验证方法 |
|---|---|---|
| 空闲 RSS（0 任务，窗口最小化到托盘） | ≤ 90MB（Linux ≤ 120MB） | 进程树 RSS 采样 10 分钟，取 p95 |
| 8 个活跃任务 RSS | ≤ 160MB | 同上 |
| 1000 条任务列表滚动 | 帧时间 p95 < 16ms，无 > 50ms 长任务 | 内置 rAF 卡顿计数器 + Performance trace |
| 进度事件上限 | 单任务 ≤10Hz，全局 ≤30Hz | 引擎侧计数器导出 |
| 4GB 单文件完成瞬间 | UI 帧时间无 > 16ms 尖峰 | 录屏 + trace 对齐完成时间戳 |
| 断点续传准确性 | 续传后文件与一次性下载 SHA256 一致 | 自动化用例：随机 kill -9 五轮 |
| 连接数 | 峰值 ≤ 设定上限，每主机 ≤ 6 | 抓包/引擎统计 |
| 冷启动 TTI | 见 3.4 | 20 次循环脚本取分位数 |

这些指标进 CI：`cargo bench` + 本地 HTTP 服务器 + 自动化脚本，任一回归超阈值即红灯。

## 4. 视频下载（编码与分辨率可选）

### 4.1 选型：yt-dlp 作为 sidecar，而不是当库

**结论：把 yt-dlp 编译后的独立二进制随包分发（或首次使用时下载），用子进程 + JSON 通信。** 【已验证：yt-dlp 官方发布 Windows/macOS/Linux 独立可执行文件】

理由：
- 当库用要嵌 CPython（+30~60MB，启动 +200ms，还要处理 GIL 与依赖地狱），且会失去"随时换新版修站点"的能力；
- 站点解析是**持续腐烂型**资产，必须能独立于主程序热更新——子进程边界让这件事只换一个文件；
- 它是 GPL/Unlicense 生态的成熟工具，社区每天在修 extractor，自研等价物不可能跟上。【已验证：其更新频率】

### 4.2 如何拿到"完整清单"并在 UI 表达

两步：
1. `yt-dlp -J --no-playlist --no-warnings <url>` → 完整 JSON，取 `formats[]`。
2. 我们自己解析，不依赖它的文案，字段映射成 UI 列：

| UI 列 | JSON 字段 |
|---|---|
| 分辨率 | `width` × `height` / `resolution` |
| 编码 | `vcodec`（av01 / vp9 / avc1 / hev1） |
| 帧率 | `fps` |
| 容器 | `ext` |
| 码率 | `tbr` / `vbr` / `abr` |
| HDR | `dynamic_range` |
| 体积 | `filesize` 或 `filesize_approx`（无值则按 `tbr × duration` 估算并标"约"） |
| 音频 | `acodec` / `asr` / `audio_channels` / `language` |
| 协议 | `protocol`（https / m3u8 / dash） |
| 是否受保护 | `has_drm` → **true 时整行禁选并解释** |

**UI 表达（差异化重点）**
- 表格化，可按体积/分辨率/码率排序，做 `video-only` 与 `audio-only` 两栏，用户自由组合；
- 默认给一个"推荐组合"（兼容性优先，而非最高画质），但可一键改；
- **兼容性徽标**：结合用户选择的"目标设备/软件"（剪辑软件、iPhone、电视盒子）提示"AV1 不被 Premiere 识别""VP9 在 Safari 不支持"，这是"更强"的体感来源；
- 明确显示"预计体积"和"下载后按字节与时长双向校验"。

### 4.3 两条下载路径

- **Path A（直连，优先）**：`formats[].url` 是可直接 GET 的媒体地址（含 `http_headers`）。我们**用自己的引擎**下载 → 分段、续传、限速、队列全部生效。必须带上 `Referer/User-Agent/Cookie` 等头部。
- **Path B（委派）**：解析需要特殊处理（签名 `nsig`、复杂 HLS/DASH、直播回放）。交给 yt-dlp 子进程下载，用 `--progress-template` + `--newline` 把进度回灌到我们队列，UI 上标记为"由解析器接管"。这类任务不支持分段限速，要在 UI 说明差异。
- 两者的**格式清单来自同一次 `-J`**，UI 体验一致。

**过期问题（重要）**：直链 URL 通常几小时内失效且绑 IP/会话。所以持久化的是"可再解析的描述符（URL + 已选 format_id）"，续传前先做一次轻量 re-resolve 校验，失效则自动重解析，最多 3 次。

### 4.4 避免维护噩梦

1. **版本钉住 + 清单校验**（SHA256），发布前在 CI 跑冒烟集：20 个公开站点，验证"能拿到 ≥1 个 format 且体积字段合理"。【待验证：冒烟集是否稳定，需观察】
2. **热更新通道**：拉取新版二进制 → 5% 灰度 → 24h 无异常再全量 → 保留上一版可回滚。
3. **失败可解释**：解析失败展示分类（站点改版 / 需要登录 / 受 DRM / 网络），并提供"用浏览器打开""上报样本"（只上报 URL 域名 + 错误码，不上报 Cookie）。
4. **不 fork**：只向上游提交补丁，绝不分叉维护 extractor 副本。
5. **降级路径**：解析不可用时，用户仍能用嗅探拿到 HLS 直链手动下载。

### 4.5 边界

- `has_drm: true` 或探测到 Widevine/PlayReady/FairPlay → **直接拒绝**，文案说明"该内容受版权保护，本工具不处理"。
- 不内置任何"绕过登录/付费/区域限制"的参数模板。
- 首次使用时展示一次性合规声明（用户确认"仅下载自己有权获取的内容"）。

## 5. 资源嗅探

### 5.1 三条路线对比

| 维度 | ① 扩展 + Native Messaging | ② CDP（`chrome.debugger`） | ③ 本地代理 + MITM 证书 |
|---|---|---|---|
| 覆盖范围 | 已装扩展的浏览器标签页，含 iframe/Worker 请求 | 同左，且可读响应体 | **全系统流量**，含非浏览器应用 |
| 安装门槛 | 装扩展（低） | 需开调试权限、Chrome 显示"正在被调试"横幅 | **装根证书 + 改系统代理（高，且吓人）** |
| 安全风险 | 低（仅本浏览器） | 中（调试通道权限大、与 DevTools 互斥） | **高**（CA 私钥若泄露等于全局中间人） |
| 企业/受管机器 | 通常可用 | 可能被策略禁 | **多数被策略/杀软拦** |
| 反制 | 站点对扩展无感 | 会被检测到调试器 | 证书固定（pinning）、TLS1.3/ECH 会让其失效 |
| 拿 manifest 正文 | 扩展有 host 权限可 `fetch` 跨域清单 → **可以** | 可以 | 可以 |
| 隐私暴露面 | 小 | 中 | **大（能看到全部流量）** |

【已验证：MV3 仍保留观察型 `chrome.webRequest`；扩展对 host_permissions 内域名可跨域 fetch】

### 5.2 结论

**默认：① 扩展 + Native Messaging 为主，② CDP 作兜底；③ MITM 代理默认关闭、白名单、需二次确认。** 理由：嗅探真正需要的是**URL + 头部 + 清单正文**，扩展路线全都拿得到，不需要碰证书；证书方案在受管机器、杀软、pinning 面前成功率低，支持成本极高，还把一个"下载工具"变成"全流量可见的中间人"——这是产品定位风险，不只是技术风险。

**③ 的合理用途**：抓非浏览器应用（桌面播放器、某些嵌入式浏览器）的流量。因此保留，但：
- 仅对用户显式加入的域名白名单生效；
- CA 私钥生成在本机、存系统钥匙串、可一键删除，绝不联网上传；
- 开启时有明确的风险文案与"我知道我在做什么"确认；
- 默认不记录 URL 之外的内容（不存响应体、不存 Cookie 明文）。

### 5.3 HLS / DASH 解析与合并

- **HLS**：主清单 → 变体（`BANDWIDTH`/`RESOLUTION`/`CODECS`）→ 媒体清单（`EXTINF` 时长、`EXT-X-BYTERANGE` 字节区间、`EXT-X-KEY`）。
  - 有 `BYTERANGE`：直接走**定位写直下**（最快路径，等同普通分段下载）。
  - 无区间：按序分片下载，**有序写入窗口**（乱序到达先进重排缓冲，超出窗口才落临时分片），最终一次顺序拼接。
  - 标准 `AES-128`（密钥 URI 在清单里公开）：属常规封装加密，不是访问控制；用用户自己的会话去取密钥即可。【边界见 §8】
  - TS 分片：拼接后用 ffmpeg `-c copy` 转封装为 MP4（不重编码，秒级）；fMP4：init + 分片拼接即可。
- **DASH**：解析 MPD（`SegmentTemplate`/`SegmentList` + `BaseURL`），按 Representation 的 `codecs` 展示编码选项，与视频格式选择共用同一套 UI 模型。
- **失败兜底**：清单异常时把 URL 交给 yt-dlp（Path B）。

### 5.4 批量嗅探：去重与筛选

**去重键**
```
canonical = scheme + "//" + lower(host) + path
            + 保留签名类查询参数（token/expires/sig/key）
            + 丢弃追踪参数（utm_*, fbclid, gclid, ref, spm, _t）
```
**媒体族合并**：同一主清单 URL 派生出的 N 个变体 → 合并成一张"媒体组"卡片，内部展开选择（这正好复用视频格式矩阵）。
**内容指纹**：`(content-length, ETag/Last-Modified)` 相同且 URL 不同 → 标"疑似重复"，默认不勾选，用户可展开对比。
**不做**：仅按文件名去重（误杀率太高）。

**筛选 UI**：类型 chips（视频/音频/图片/文档/HLS/DASH/字幕）· 最小体积滑杆 · 最低分辨率 · 域名多选 · 关键词搜索 · "隐藏广告/统计/埋点"启发式开关（按 MIME + 尺寸 + 已知追踪域名后缀，可关）。
**批量选择**：组内全选、Shift 区间选择、"预设选择"（全部视频 ≥720p / 全部图片 >500KB / 仅主媒体族）、底栏实时汇总"已选 12 项 · 1.82GB"。

**隐私**：嗅探结果仅本地存储，默认 24h 自动清理，可一键清空；不写日志到远端。

### 5.5 嗅探的合规风险面（要写进产品）

| 风险 | 说明 | 处理 |
|---|---|---|
| 抓到自己账号下的付费内容 | 技术上抓得到，但可能违反站点条款 | 首次使用合规声明；不提供"批量抓某站整季"的引导 |
| 代理模式看到全部流量 | 隐私与误用风险 | 默认关闭、白名单、私钥入钥匙串、可审计开关 |
| 证书被用于其他目的 | 用户可能拿 CA 去做别的事 | 证书仅在本进程内可导出链，卸载即删；文档明确警告 |
| 站点条款禁止下载（即使无 DRM） | 法律灰区 | 在产品内显示"你对所下载内容负责"；不内置规避建议 |

### 5.6 浮动下载条：能否"只在有视频时出现"

**结论：能，但必须分三档说清楚。** "显示/不显示"这个开关本身不难，难在两件事：可靠判定"这一页到底有没有可下载的视频"；把条塞进跨域 iframe 或全屏播放器里。

**判定信号（按置信度排序）**
1. **网络层**（观察型 `webRequest`，MV3 仍可用）：响应头 `Content-Type: video/*` 且同时有 `Content-Length` 与 `Accept-Ranges: bytes`；或 URL / 类型命中 `.m3u8`（`application/vnd.apple.mpegurl`）、`.mpd`（`application/dash+xml`）。跨 iframe 也看得见。
2. **媒体元素**（content script，`all_frames:true`）：`<video>/<source>` 的 `src`、`currentSrc`、`duration`、`readyState`。`blob:` 说明是 MSE（hls.js / dash.js / shaka），真实地址 DOM 里拿不到，只能靠第 1 条。
3. **分片证据**：同一 URL 连续出现 `206` 且 `Content-Range` 递增 → 分段媒体。
4. **反例过滤**：`duration < 30s`、`muted + autoplay + loop`、已知广告位域名 → 不出条。

再过一道"可下载"闸：manifest 含非 AES-128 的 `#EXT-X-KEY`、MPD 含 `ContentProtection`、`navigator.requestMediaKeySystemAccess` 能协商出 Widevine / PlayReady / FairPlay → 判定受保护，**不出条、不入队**。

**三档**

| 档 | 场景 | 能否稳定 | 处理 |
|---|---|---|---|
| **A 稳定** | 同源或已授权域名的普通 `<video src>`；HLS 主清单；DASH；渐进式 MP4；域名已授权的 iframe 播放器；SPA 后动态插入的播放器 | 是 | content script 常驻 + MutationObserver + webRequest 双信号，"或"命中即出条 |
| **B 尽力** | `blob:`/MSE 播放器；未授权跨域 iframe（可用 `optional_host_permissions` 运行时申请）；全屏播放；闭合 Shadow DOM 的播放器；广告与正片共用一个播放器 | 大概率，但会漏也会误 | 网络层兜底 + 条挂顶层 frame；全屏时迁移宿主或退化为工具栏徽标 |
| **C 做不到** | DRM（Widevine/PlayReady/FairPlay）；WASM/私有协议传输（WebSocket、自定义加密）；未授权跨域 iframe 且顶层页也未授权；非浏览器播放器 | 否 | 不出条；只能手动粘贴链接，或用用户自选的证书代理 |

补充：C 档里的"未授权 iframe"能用 `optional_host_permissions` + 用户点一次提升到 B/A；**真正无解的是 DRM 与私有传输**。

**CSP 与 Shadow DOM 的真实影响**
- 页面 CSP **不拦 content script 的执行**（隔离世界），也不拦往 DOM 插节点；会被 CSP 拦的是"往主世界注入 `<script>`"这种做法。
- 样式要小心：优先 `manifest.content_scripts.css`（浏览器按用户样式注入，不受 `style-src` 约束），或在隔离世界构造 `CSSStyleSheet` 走 `adoptedStyleSheets`；**不要用 `innerHTML` 拼 UI**（Trusted Types 站点可能抛错），全部走 `createElement`。【待实测：严格 CSP 站点上的注入样式表现】
- Shadow DOM 用 `mode:'closed'`，宿主挂 `document.documentElement`（**不要挂 body**，SPA 重渲染会连条一起清掉），`position:fixed` + `z-index:2147483647`，宿主 `pointer-events:none`、面板 `auto`。
- 页面 JS 仍可删掉宿主 → `MutationObserver` 盯根节点子元素变化，节流 200ms 自愈重挂。

**注入方式对比**

| 方式 | 抗站点 CSS | 抗页面 JS | 全屏/滚动 | 结论 |
|---|---|---|---|---|
| closed Shadow DOM + fixed 宿主 | 强 | 中（可被删，需自愈） | 需处理 `fullscreenchange` | **推荐** |
| 直接插页面 DOM | 弱（被站点样式覆盖） | 弱 | 一般 | 不推荐 |
| `iframe` 指向 `chrome-extension://` 页面 | 最强（完全隔离） | 强 | 定位与尺寸同步麻烦 | 备选 |
| 工具栏 `action` 徽标 | — | 不受影响 | 不受影响 | **必做兜底** |

产品上定两条：**浮动条是主路径，工具栏徽标是永远准确的兜底**——条被吞、全屏、iframe 受限时用户仍有退路，"这一页有几个可下载"这个数字不会骗人。

至于"其余资源不显示条"：普通文件 / 图片 / 文档只走**静默接管**（`Content-Disposition: attachment` 或主框架导航即下载），不进入浮动条判定，避免条到处乱弹。

## 6. 队列模型与重试

**任务状态机**
```
queued → resolving(视频/清单) → connecting → downloading → postprocess(转封装/校验)
       → completed | failed | paused | waiting_retry | needs_attention
```

**调度**
- 优先级两级：前台（用户手动）> 后台（批量）。
- 任务级 DRR 分配"带宽份额 + 连接份额"，另设全局并发上限（默认 `max(2, 核数/2)`）。
- 单任务可临时提权（右键"加速此任务"），有效期 10 分钟。

**重试策略**
- **分段级**：失败的段从最后一个成功字节续（Range 请求），指数退避 `2→4→8→16→32→60s`，抖动 ±20%，最多 5 次。
- **错误分类**：
  - 永久：404、410、DRM、明显的内容不存在 → 不重试；
  - 会话类：403/签名过期 → **重解析**（视频 ≤3 次），失败转 `needs_attention`；
  - 拥塞类：429（遵从 `Retry-After`）、5xx、连接重置、超时 → 退避重试；
  - 本地类：磁盘满、权限 → 暂停并提示，不消耗重试次数。
- **批量语义**：批量 = 一组**独立任务** + 批次聚合视图，不是一个大 Job。批次有自己的失败阈值（如"失败率 > 30% 则暂停整批"），单项失败不影响其他项。
- **去重**：入队时按 canonical URL + 体积比对历史，命中则提示"已有相同文件（已完成/部分）"。

**持久化**
- SQLite（WAL），表：`tasks / segments / batches / sniff_sessions / settings`。
- 分段进度以 bitset 存（每 2s 或 32MB checkpoint 一次）。崩溃恢复：校验文件大小与 bitset 重同步。

## 8. 法律与平台条款边界

**产品内必须固化的规则（不是文案，是代码）**
1. 只处理用户有权获取的内容；
2. **不实现** DRM 解密、许可协商、密钥获取；检测到受保护流即终止；
3. **不实现**付费墙、登录墙、地域限制、验证码的绕过；需要登录的内容只使用**用户自己在浏览器中的会话**，且不代存、不上传；
4. 不提供"站点头像化"的批量抓取引导，不内置侵权站点清单；
5. 嗅探数据仅本地、默认自动清理；代理模式默认关闭。

**灰区但要如实告知**：即使无 DRM，部分平台条款仍禁止下载。产品以"用户自担责任"的一次性声明呈现，不提供法律建议，也不做"如何规避"的帮助文档。

### 8.1 硬边界：不存在"绕过保护措施"的版本（含私有/内部/不发布）

**结论：不做。任何形态都不做——不对外发布、只给自己用、只给内部团队用，都不构成例外。**

**话要说到位的理由**
- 依据是《中华人民共和国著作权法》第五十三条（规避技术措施属侵权行为，可追究民事/行政责任，情节严重涉刑）与 DMCA §1201（规避访问控制技术措施本身即违法，不以"是否复制作品"为前提）；欧盟 InfoSoc 指令第 6 条同类。
- "仅自用/不传播"**不是豁免**：DMCA §1201 规制的是"规避行为"本身；国内司法实践同样看"是否规避技术措施"，而不是看有没有拿去卖。私有版本不改变行为的违法性质，只减少被发现的概率——不能把"降低被发现概率"当作可行性依据。
- 一旦写了这条代码，它就成为可被复制、被流传、被截图背书的东西；产品定位会从"下载管理器"滑向"破解工具"，后续无论怎么声明都洗不回来。
- 因此这不是"法务建议"，是**产品范围决策**：写死在需求里，任何"通融一下"的诉求都按本条款直接拒绝。

**落到实现与 UI（不是文案，是行为）**
1. **识别即拒绝**：检测到 `has_drm: true`、Widevine/PlayReady/FairPlay、或清单/密钥端点明显属于访问控制（如加密分片 + 许可证服务器）时，任务在入队前终止。
2. **明确提示，不静默失败**：UI 显示"该内容受保护，无法下载"，并给出"为什么"（受 DRM/访问控制保护）与"可以做什么"（用官方客户端、联系内容方）；**不得**降级为"尝试最高画质""换协议再试""用解析器接管"等隐性尝试路径，也不得把失败包装成"网络错误"。
3. **不猜、不试、不绕**：不实现密钥获取、许可证协商、CDM 调用、解密后处理，也不提供任何"参数模板"。
4. **不碰凭证**：不实现 cookie 窃取/导出、账号借用、验证码识别、指纹伪造；需要登录的内容只用用户**自己当前浏览器会话**发起请求，且不落盘、不上传、不跨账号复用。
5. **不做"什么都能下"的叙事**：功能列表、官网、更新日志、客服话术里都不出现"支持所有网站""破解/解锁/无水印"这类表述；对外统一口径为"下载你有权获取的内容"。
6. **可审计**：拒绝事件只本地记录（域名 + 原因码，不含 URL 全文、不含 Cookie），便于自查"我们确实没有尝试绕过"。

**如果将来有人提"私有版本"需求**：标准答复是"该需求不在产品范围内，且实现即违法"，不进入排期、不做技术预研、不写 PoC。

3. **Tauri vs Electron**：是否接受"三平台 WebView 存在渲染差异"这一代价换取内存与启动优势？
   - **定了会怎样**：Tauri → v1 三平台各做一轮 WebView 渲染回归（设计稿已按克制视觉出）；Electron → 内存与冷启动目标（§3.5）整体作废，需重写验收基线。
4. **Linux 支持深度**：Flatpak 沙箱会限制"全局代理/证书"能力。是否接受 Linux 为**功能子集**（无系统级代理模式），以此换取干净的打包与分发？
   - **定了会怎样**：接受子集 → v1 Linux 只保留下载引擎 + 扩展嗅探，打包与签名工作量可控；不接受 → v1 需为 Linux 单独做发行版矩阵与代理方案，交付面显著变大。
5. **浮动下载条的上限**（见 §5.6）：是否接受"B 档尽力而为"——DRM 页面、私有传输、未授权跨域 iframe 不显示浮动条，只保留工具栏徽标兜底？
   - **定了会怎样**：接受 B 档 → v1 浮动条覆盖主流站点，边界情况以徽标兜底，无额外风险；要求 A 档 → 必须引入更深的页面注入与跨域授权策略，安全评审与站点兼容成本上升。

如果上述 1~5 项都按"建议值"走，第一版范围就是：**Win/macOS 全功能 + Linux 功能子集 + Chromium/Firefox 扩展 + 自带 yt-dlp/ffmpeg + 无 MITM 默认开启**。

## 10. 扩展分发：不上架商店怎么装

> 前提：本产品的浏览器集成只有扩展这一条路（浮动条、静默接管、清单正文抓取都依赖它）。所以"能不能装"直接决定获客成本。

### 10.1 逐浏览器结论

| 浏览器 | 方式 | 实际限制 | 用户操作成本 | 适用 | 置信度 |
|---|---|---|---|---|---|
| **Chrome** | 开发者模式 Load unpacked | 每次启动仍会弹"停用开发者模式扩展"提示；正式版自 Chrome 137 起移除了 `--load-extension` 启动参数（Chromium / Chrome for Testing 仍可用）；Chrome 升级不会卸载扩展 | 中：开开发者模式 → 拖目录 → 每次启动点掉提示 | 内测、早期用户 | 【已验证】 |
| **Chrome** | 自托管 `.crx` 拖拽安装 | 正式版 Win/macOS 直接拦截非商店 CRX（`CRX_REQUIRED_PROOF_MISSING`），拖拽无效 | 不可行 | — | 【已验证】 |
| **Chrome** | 企业策略 `ExtensionInstallForcelist` + 自托管 `update.xml` | 仅在**受管设备**生效（HKLM 策略 / MDM / 域）；普通个人机器写注册表需管理员且未受管时策略不生效 | 组织内为零 | B 端 | 【已验证】 |
| **Edge** | Load unpacked | 同 Chromium；同样有开发者模式提示（界面与频率比 Chrome 温和） | 中 | 内测 | 【待实测：最新版提示行为】 |

| **Firefox** | 企业策略 `force_installed` | 受管环境 + 自托管 XPI | 组织内为零 | B 端 | 【已验证】 |
| **Safari (macOS)** | **不发布**；仅开发者本机用 Xcode 签名运行容器 `.app`（内含 `.appex`，实验性自测） | 需 macOS + Xcode 本机签名；「允许未签名扩展」是开发者开关，**Safari 每次重启都会重置**；不做签名/公证流水线，不写对外安装说明 | 开发者内部：中（每次重启重开开关） | **不入 v1 发布范围** | 【已验证：机制】 |
| **Safari (iOS/iPadOS)** | 只能 App Store（或 TestFlight / 企业分发） | 消费者侧没有站外安装 | 高 | 第一版不支持 | 【已验证】 |

### 10.2 推荐的分发路径

1. **Chromium 系（Chrome + Edge）一份产物两个 manifest 变体**：主分发走 **Edge 加载项商店**（成本最低的"正经"分发，用户一键装且自动更新）；同时保留"开发者模式离线包"给内测与受管环境；B 端另出自托管 + 策略模板。
2. **Firefox 复用源码**，构建时切换 background 形态（event page vs service worker）、补 `browser_specific_settings`、API 走 `webextension-polyfill`；分发走 **AMO unlisted 签名 + 自托管**。
3. **Safari 不进 v1 发布路径**：不做 Xcode 工程、不做签名/公证、不建议装进安装说明。只在架构上保留 §10.4 说的"扩展能力降级层"，等有付费开发者账号且决定对外支持时再补那套工程；对外口径统一为"支持 Chrome / Edge / Firefox"。
4. **桌面端安装包负责收尾**：注册 Native Messaging 宿主（Windows 写 `HKCU\Software\Google\Chrome\NativeMessagingHosts\<name>`，**不需要管理员**；macOS 写 `~/Library/Application Support/...`；Firefox 写 `~/.mozilla/native-messaging-hosts`），并在首次启动时引导用户完成扩展安装。Safari 本机自测走 Xcode 容器 App 自带的 handler，不进发行包。

### 10.3 "一套代码多浏览器"的真实成本

| 目标 | 复用程度 | 额外工作 |
|---|---|---|
| Chrome + Edge | ~100%（同一份 MV3） | 两个 manifest 变体、两份商店素材 |
| Firefox | ~90%（共用 JS/CSS） | 1 个构建目标 + polyfill 适配 + 权限声明差异 |
| Safari | 只复用 JS/CSS，**不复用打包** | v1 为零；只在共享代码里留能力开关（见 §10.4）。若将来转正：1 个 Xcode 工程 + 证书/公证 + 功能降级表 + 逐站点授权 UX |

**一句话结论**：v1 的答案就是 **Chromium + Firefox 同仓构建**；Safari 只保留"降级层"接口、不做工程，也不做宣传。将来若要支持，再单列工程并接受功能降级。

### 10.4 Safari：实验性支持，仅限开发者本机自测

**定位（已拍板）**
- 不对外发布：不提供下载入口、不写进功能列表/官网/宣传口径，不承诺版本支持；
- 不做独立签名/公证流水线，不申请 Developer ID、不建 `notarytool` 步骤；
- v1 对外只承诺 Chrome / Edge / Firefox。

**本机自测的现实约束（要如实写进内部文档）**
- 需要 macOS + Xcode，用本机签名把容器 App 跑起来（免费个人团队签名即可，有效期短，到期重签）；
- Safari 的「允许未签名扩展」是**开发者开关**（开发菜单 → 允许未签名扩展），**Safari 每次重启都会重置**，每次自测都要重新打开并重新勾选扩展；
- 没有 `chrome.debugger` / CDP 兜底，嗅探只能依赖扩展自身能力，浮动条与"静默接管"覆盖范围明显小于 Chromium；
- 因此 Safari 的验证结论只能作为"能力上限参考"，不能当作对外质量承诺。

**不写进安装说明的做法**
- 不使用"右键打开""`xattr -d com.apple.quarantine` 去隔离属性""临时关闭系统完整性保护/降低 Gatekeeper"这类绕过系统安全的步骤；
- 若某台机器因签名/隔离无法运行，结论就是"该环境不支持"，而不是给用户一套降级系统安全的操作指南。

**架构上保留的"扩展能力降级层"（现在只留接口，不建流水线）**
- 引擎侧启动后上报一份能力表，例如 `sniff.responseBody`、`sniff.webRequest`、`ext.backgroundPersistent`、`ext.floatingBar`、`ext.nativeMessaging`、`debug.cdp`；
- 共享扩展代码与 UI 只读能力表决定"显示/隐藏/降级"，不写 `if (isSafari)` 之类的浏览器分支；
- 缺能力时给"该浏览器不支持此功能"的明确说明，而不是静默失败或报错刷屏；
- 该层对 Chromium/Firefox 是满能力直通，因此 v1 用它不会增加额外成本。

**转正条件（触发才做）**
- 有付费 Apple Developer 账号；且明确要把 Safari 列入对外支持。届时再补：Xcode 工程（`safari-web-extension-converter` 包装共享 JS）、签名与公证流水线、逐站点授权的 UX 与支持文档。在此之前，只维护能力表与降级分支的可编译性。

## 12. 更新器规格（对齐 Pathleap 的交互基准）

### 12.1 参考结论：Pathleap 没有可复用的更新器实现

`yunyu697/pathleap`（private，默认分支 main）是 .NET/WPF 的 M1 骨架。**可以借鉴的**已落地：版本号单一来源与硬校验规则、tag `v` 前缀、CI 在 tag 触发打包；这些已在本仓库照搬（`version.json` + `tools/Test-FwVersion.ps1` + `.github/workflows/release.yml`）。

**不可借鉴的**：其仓库与文档中更新模块标注为 **M3（未实现）**，没有更新器、镜像配置与状态机的代码可读。因此本节按用户给定的交互规格自行落地，**不存在"两边行为不一致"的可比对象**，后续 Pathleap 若实现更新器需要反过来对齐本节。

### 12.2 常驻与条件按钮

| 条件 | 可见按钮 |
| --- | --- |
| 常态 | **检查更新**、**打开主页** |
| 检测到新版本 | 追加 **更新**、**仅下载**，并显示：版本号、更新说明、镜像选择下拉 |
| 仅下载完成 | 该区域改为 **安装**、**打开下载目录** |

- **更新** = 自动下载 → 安装 → 重启。
- **仅下载** = 下载到系统默认下载目录，不安装；下载完成后按钮组切换为"安装 / 打开下载目录"。
- 两种方式都走加速镜像，且允许用户手动切换；切换即时生效并记忆选择。

### 12.3 状态机

```
idle ──检查更新──► checking ──┬─► up-to-date（显示"已是最新"）
                              └─► update-available（显示版本号/说明/镜像下拉 + 更新/仅下载）
update-available ──更新──────► downloading ──► verifying ──► installing ──► restarting
update-available ──仅下载────► downloading ──► downloaded(external) ──► 安装 / 打开下载目录
downloading ──失败──► download-failed（可重试，保留镜像切换）
任何状态 ──取消──► idle（已下载字节可续）
```

- 预发布版本（`-alphaN`）之间按 semver 预发布顺序比较，`alpha10 > alpha9`，`1.0.0 > 1.0.0-alphaN`。
- 检查更新只读自有仓库 Releases（`api.github.com/repos/yunyu697/fetchweir/releases`），**不执行从任意 URL 拉来的安装包**。
- 资源匹配按平台后缀：Windows `*-setup.exe`（NSIS）、macOS `*.dmg`、Linux `*.AppImage` / `*.deb`。

### 12.4 镜像策略

- 默认直连 GitHub；内置若干只做**前缀转发**的加速镜像（不改变资源内容），由用户在下拉中切换。
- 镜像不可用时自动回退到下一个候选，全部失败再提示"切换镜像或稍后重试"，不静默失败。
- 下载完成后校验 `Content-Length` 与实际字节数一致；正式版启用签名校验（见 §12.5）前，至少校验文件名与平台匹配。

### 12.5 分平台安装

| 平台 | "更新"的行为 | 说明 |
| --- | --- | --- |
| Windows | 静默运行 NSIS 安装包后退出主程序 | 提供「当前用户」与「所有用户」两种包；更新沿用用户当初选择的安装范围，不跨范围静默替换 |
| macOS | 打开 dmg 引导用户完成，随后退出 | 无公证前不做静默替换；正式发布补签名与公证 |
| Linux | 打开 AppImage / 提示用包管理器安装 deb | 与 §10 的分发结论一致 |

### 12.6 实现状态（v1.0.0-alpha2 开发线）

已落地：`src-tauri/src/update.rs` + 设置页「更新」卡片。行为与 §12.2–12.5 对齐，差异点单列。

- **检查**：只读 `api.github.com/repos/{updateRepo}/releases`，草稿跳过；按平台后缀挑包（Windows `*-setup.exe`、macOS `*.dmg`、Linux `*.AppImage` 优先、`*.deb` 兜底）。预发布按 semver 预发布序比较：`alpha10 > alpha9`，`1.0.0 > 1.0.0-alphaN`。
- **私有仓库**：仓库当前为 private，需在设置里填「访问令牌」，或设置环境变量 `FETCHWEIR_GITHUB_TOKEN`。未配置令牌时返回明确原因，不静默失败。
- **镜像**：内置 GitHub 直连 / ghfast.top / gh-proxy.com 三个**前缀转发**镜像，下拉切换即时保存；公开仓库下载按「所选镜像 → 其余镜像」顺序自动回退，全部失败才报错。私有仓库的资源只能走带令牌的 API 端点，镜像不参与（代理无法携带鉴权）。
- **下载**：`.part` 断点续传（取消后保留已下载字节）；`Content-Length` 与落盘字节数一致才判定成功。「仅下载」落到系统默认下载目录，「更新」落到数据目录 `updates/`。
- **安装**：Windows 走 NSIS `/S` 静默安装，由独立 PowerShell 等待安装完成后再拉起新版本；macOS 打开 dmg 后退出；Linux 给 AppImage 赋可执行位后启动，deb 打开所在目录交给系统安装。
- **与规格的差异**：取消后状态回到 `updateAvailable`（保留断点），而不是规格里的 `idle`；这样按钮组不会消失，用户可直接续传。

**本机实测（Windows，2026-11-07，全部后台/无界面运行）**

| 场景 | 触发方式 | 结果 |
|---|---|---|
| 私有仓库带令牌检查 | `FW_UPDATE_PROBE=1` | `stage=upToDate`，识别 alpha2 与四个平台产物 |
| 私有仓库无令牌检查 | `FW_UPDATE_PROBE=1` | `stage=failed`，提示「更新源不可访问……请填写访问令牌」 |
| 「仅下载」完整链路 | 版本临时置 alpha0 + `FW_UPDATE_FETCH=1` | `stage=downloaded`，1385827 字节与 `assetSize` 完全一致，落点 `%USERPROFILE%\Downloads` |
| 版本比较 / 镜像顺序 / 文件名净化 | `cargo test` | 6 个单测通过 |

**尚未覆盖**：正式版签名校验（发布前补）、macOS dmg 与 Linux AppImage 的安装动作仅有代码路径（本机无对应环境）。

## 13. 安装范围、权限与单实例（Windows 实现状态）

细节与逐项命令记录见 [安装范围与权限.md](安装范围与权限.md)，这里只留产品/架构结论。

### 13.1 两种安装范围并存，数据与程序分离

| | 仅当前用户（默认） | 所有用户 |
| --- | --- | --- |
| 安装目录 | `%LOCALAPPDATA%\Fetchweir` | `%ProgramFiles%\Fetchweir` |
| 快捷方式 | 当前用户开始菜单 + 桌面 | 公共开始菜单 + 公共桌面 |
| 卸载项 | `HKCU\...\Uninstall\Fetchweir` | `HKLM\...\Uninstall\Fetchweir` |
| 数据 | `%APPDATA%\Fetchweir` | 每个用户各自的 `%APPDATA%\Fetchweir` |
| UAC | 不需要 | 安装与卸载都需要 |

数据目录与安装目录分离是硬约束：用户级安装目录会在卸载时被删除，设置与记录必须放漫游目录。
两种包都在本机完成过安装 → 核对 → 卸载 → 清理检查，卸载后数据保留。

### 13.2 「始终以管理员身份运行」是显式选项，不是默认

- 提权判断只看进程令牌（`TokenElevation`），不看窗口标题；实测 High 完整性级别 `S-1-16-12288`，普通为 `S-1-16-8192`。
- 开启后若同时开启自启动，`HKCU\...\Run` 会被替换为计划任务 `FetchweirElevated`（`ONLOGON` + `HighestAvailable`），
  因为 Run 项只能拉起普通权限进程。关闭选项后任务删除、Run 项按自启动设置恢复。
- 提权的代价是 UIPI：资源管理器拖入会被拦截。界面显示提示，建议粘贴链接或走扩展；
  Native Messaging 走本地回环，不受窗口完整性级别影响（提权下实测正常）。
- 默认保持普通权限：调起 UAC 会打断启动，且多数下载场景不需要管理员。

### 13.3 单实例：命名互斥量 + `WM_COPYDATA`

`tauri-plugin-single-instance` 负责互斥与转发。提权首实例的接收窗口默认拒绝低完整性进程发来的 `WM_COPYDATA`，
因此启动时用 `ChangeWindowMessageFilterEx` 只放行 `WM_COPYDATA` 一条，其余消息仍受 UIPI 约束。
实测：普通权限下第二个实例退出码 0、进程数保持 1、参数到达首实例；提权首实例同样成立。
跨用户会话不共享互斥量，不做跨用户单实例。
