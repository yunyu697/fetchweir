# 发布检查清单

发版前逐项打勾；任何一项不成立就停下，不要靠"应该没问题"放过。

## 0. 功能状态清单复核（发布闸门）

**在哪一步**：打完版本号、出包之前；也就是 `git tag` 和 `gh release create` 之前。  
**谁更新**：本次发版执行人（执行 tag/Release 的人）。  
**谁复核**：项目维护者，至少在创建 Release 前抽查所有“高”优先级行。

- [ ] 打开 [功能状态清单.md](功能状态清单.md)，逐条复核本次改动涉及的行。
- [ ] 新增/修改的功能必须有“已实现已验证”的证据链接（文档、截图、采样 JSON、CI 运行号）；
      拿不出证据的，只能写“已实现未验证”，并写清缺什么、为什么现在测不了。
- [ ] 设置页新增、删除或改名的控件，必须同步更新清单的“设置页逐项对照”和
      “界面‘未生效’控件逐项判定”两张表；界面上的“未生效/已锁定/自动”标签必须与清单一致。
- [ ] 本次发布说明里的已知限制，必须与清单第 6 节一致；不得把“未验证”写成“已跑通”。
- [ ] 发版执行人把清单顶部的“最后复核”改成本次日期；复核人确认后再打 tag。
- [ ] **未更新功能状态清单 = 发布流程未完成**：不得打 tag、不得创建 Release。
      如果已经打了 tag，发布说明必须写明“功能状态清单未更新”，并把它列为已知问题。
- [ ] 发布后 48 小时内：补齐本次新增/变化项的证据，或把状态降为“已实现未验证”。

## 1. 发布口径

- [ ] 本版发布方式：**推送 tag → CI 自动出包并上传 Release**
      （`.github/workflows/release.yml`，`permissions: contents: write`）。
      tag 上会构建两个安装范围包、校验字节差异与内嵌执行级别，再上传资产与
      `latest.json` / `latest.json.sig`。
- [ ] CI 只在 Windows x64 出包，且这是**有意为之**：
      macOS 缺 arm64 版 ffmpeg sidecar（随包的 ffmpeg 只有 x86_64 构建），也没有公证/签名凭据；
      Linux 的 deb/AppImage 安装路径（桌面集成、卸载、自启动）未实测。
      发布说明不得暗示这两个平台已产出或可用。
- [ ] 仓库需要 `FW_SIGNING_KEY` secret。缺失时流水线会打 `::warning title=发布未签名`
      并在 step summary 写明「不生成清单，客户端检测不到该版本」，此时本次发布记为
      **未签名发布**，只能手动下载安装包。
- [ ] 仓库所有者要求"只同步代码"时：只 commit + push `main`，不打 tag、不动已推送的 tag。
- [ ] CI 在构建前用 `tools/Cache-FwNsis.ps1` 预置 NSIS 工具链：tauri 打包前会去
      `github.com/tauri-apps/binary-releases/releases/download/...` 下载，该路径连续回 504
      （2026-11-08 两次 CI 均挂在此处）。脚本改走 GitHub API 资产端点并校验 sha1；
      升级 `@tauri-apps/cli` 后 NSIS 版本会变，需同步改脚本里的版本与 sha1。
- [ ] Release 已存在后不要再删/重推同一个 tag：GitHub 会把它转成草稿（`draft=true`），
      表现为 `releases/latest` 仍指向旧版本、资产直链 404、CI 的 `gh release view` 取不到该 tag。
      2026-11-08 实际踩到，需要 `gh release edit <tag> --draft=false` 转正。

## 2. 版本号

- [ ] `version.json` 是本次要发布的版本，且格式合法：
      `pwsh tools/Test-FwVersion.ps1 -FwTag vX.Y.Z` 通过（不打 tag 时去掉 `-FwTag`）。
- [ ] 需要打 tag 时，tag 名与 `version.json` 完全一致（`vX.Y.Z`）。

## 3. 本地出包

- [ ] 一条命令出两个安装范围：

      ```powershell
      pwsh -NoProfile -File tools/Build-Fw.ps1 -FwTask release
      ```

- [ ] 出包前确认两个 sidecar 都在 `src-tauri/binaries/`（不入库，需先同步一次）：

      ```powershell
      ./tools/Sync-FwYtdlp.ps1
      ./tools/Sync-FwFfmpeg.ps1
      ```

      两个脚本默认按 msvc 三平台命名；本机是 MinGW（gnu）工具链时要显式给 triple，
      例如 `-FwTriple x86_64-pc-windows-gnu`，文件名必须与构建用的 triple 一致。

      缺 ffmpeg 时构建会直接报 `resource path binaries\ffmpeg-<triple>.exe doesn't exist`；
      装上后「纯视频流 + 最佳音轨」的合并才能用（设置页会显示「就绪」）。
- [ ] 终端打印的版本号与 `version.json` 一致，`dist/` 下有两个文件：
      `Fetchweir_X.Y.Z_x64-setup.exe`（currentUser）、
      `Fetchweir_X.Y.Z_x64-setup-allusers.exe`（perMachine）。
- [ ] 记录两个包的字节数与 SHA256（命令已打印），分发时一并给出。
- [ ] 抽查内嵌 `fetchweir.exe` 的 ProductVersion/FileVersion 等于本次版本。

## 4. 清单与签名（CI 自动执行，发布后核对）

- [ ] CI 在 tag 上会自动跑下面两步；本地只在兜底或排查时手动跑。
- [ ] 生成清单：`node tools/New-FwManifest.mjs`（只收录 `dist/` 里真实存在的安装包，
      没构建的平台不会出现在清单里）。
- [ ] 签名私钥仍是 `.secrets/update-signing.pem`，**没有重新生成**。
- [ ] 私钥与 `src-tauri/src/update.rs` 的 `RELEASE_PUBKEY_B64` 配对：
      把私钥内容放进 `FW_SIGNING_KEY` 后跑 `node tools/Sign-FwManifest.mjs --in dist/latest.json`，
      不配对会以退出码 3 拒绝。
- [ ] 清单里的 `url` / `size` / `sha256` 与实际分发的安装包一致。
- [ ] 本地验签通过；改动清单任意一个字节后验签失败。
- [ ] 本次没有修改 `RELEASE_PUBKEY_B64`。若改了，视为换钥：必须先发布带新公钥的版本。

## 5. 创建 Release 与说明

- [ ] tag 打在本次发布对应的提交上（`vX.Y.Z`）。推送后 CI 自动创建 Release，
      上传两个 exe 与 `latest.json`、`latest.json.sig`（未签名发布只有两个 exe）。
- [ ] `gh release view vX.Y.Z` 核对资产名、字节数与 SHA256，
      与 `docs/evidence/` 或 CI 日志里 `Test-FwInstallers.ps1` 的打印一致。
- [ ] 需要本地兜底时，仍可 `pwsh -File tools/Build-Fw.ps1 -FwTask release` 出包后
      手动 `gh release upload`，但不要让本地包和 CI 包混在同一个 Release 里。
- [ ] 发布说明写明最低系统要求、已知限制、实际构建的平台。
- [ ] 发布说明链接到 [功能状态清单.md](功能状态清单.md)，并注明本版新增/变化的行；
      发布说明里的“已知限制”与清单第 6 节逐条一致。
- [ ] 发布说明注明哪些环节已实测、哪些未验证，不把"未验证"写成"已跑通"。
- [ ] 若本次是**未签名发布**（缺 `FW_SIGNING_KEY`），发布说明必须写明
      「自动更新不可用，需手动下载安装包」。
- [ ] 若启用了自动更新且签名密钥与旧版本不同：必须提醒 **1.0.0 ~ 1.0.3 用户
      手动下载安装包**，这些客户端内置旧公钥，对新钥签的清单验签会失败。
