# 发布检查清单

发版前逐项打勾；任何一项不成立就停下，不要靠"应该没问题"放过。

## 1. 版本与产物

- [ ] `version.json` 与本次 tag 一致（`tools/Test-FwVersion.ps1 -FwTag vX.Y.Z` 通过）。
- [ ] 两个 Windows 安装包齐全：`Fetchweir_X.Y.Z_x64-setup.exe`（currentUser）与
      `Fetchweir_X.Y.Z_x64-setup-allusers.exe`（perMachine），版本号写在文件名与文件属性里。
- [ ] 每个产物的 SHA256 已记录，且与清单里的 `sha256` 完全一致。
- [ ] 清单 `assets` 覆盖本次所有平台的产物；识别不了平台的产物不要留在 `dist`。

## 2. 发布密钥（固定，不换）

- [ ] 签名私钥仍是本机 `.secrets/update-signing.pem`，**没有重新生成**。
- [ ] 私钥推导出的公钥与 `src-tauri/src/update.rs` 的 `RELEASE_PUBKEY_B64` 一致。
      跑一次签名即可验证：不一致时 `tools/Sign-FwManifest.mjs` 会以退出码 3 拒绝。
- [ ] CI secret `FW_SIGNING_KEY` 是同一把私钥；流水线里没有任何生成密钥的步骤。
- [ ] 本次没有修改 `RELEASE_PUBKEY_B64`。若改了，视为换钥：必须先发布带新公钥的版本，
      不能在同一次发版里既换钥又要求老客户端自动更新。

## 3. 清单与签名

- [ ] `latest.json` 与 `latest.json.sig` 都由 `tools/Publish-FwRelease.ps1` 生成，签名非空。
- [ ] 本地验签通过，且改动清单任意一个字节后验签失败（篡改必须被拒）。
- [ ] 清单 `version` 高于现有线上版本；预发布版本不要推给正式版用户。

## 4. 兼容与说明

- [ ] 发布说明写明最低系统要求与已知限制。
- [ ] 若本次签名密钥与旧版本内置公钥不同：发布说明必须提醒 **1.0.0 ~ 1.0.3 用户
      手动下载安装包**，这些客户端对新钥签的清单验签会直接失败。
- [ ] 发布说明里注明哪些环节已实测、哪些未验证，不把"未验证"写成"已跑通"。

## 5. 发布口径

- [ ] 确认当前是否允许打 tag / 创建 Release。仓库所有者要求"只同步代码、不发版"时，
      只 commit + push `main`，不打 tag、不建 Release、不重跑已有 tag 的流水线。
