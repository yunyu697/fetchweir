# 更新机制（v1.0.4 起）

## 当前发布口径（先看这里）

- 源码仓库已公开（`yunyu697/fetchweir`），更新源与 Release 都在**同一个仓库**，
  不再维护单独的产物仓库。
- 默认更新源：`https://github.com/yunyu697/fetchweir/releases/latest/download`，
  客户端只读、零令牌。
- **安装包在本地构建，Release 手动创建**：CI 在 tag 上只校验 `version.json`，
  不打包、不上传。流程是
  `pwsh tools/Build-Fw.ps1 -FwTask release` → `node tools/New-FwManifest.mjs` →
  `node tools/Sign-FwManifest.mjs` → `gh release create`，把两个 Windows 安装包与
  `latest.json` / `latest.json.sig` 一起挂到该 tag 的 Release。
- v1.0.4 本轮**只构建了 Windows x64**；macOS dmg 与 Linux deb/AppImage 未在本地构建，
  清单与 Release 里都不会出现这两个平台的资产。本版也没有 macOS/Linux 可运行产物；
  「没有适用于当前平台与架构的安装包」这条提示只有选择逻辑的单测覆盖，未在 mac/Linux 实机跑过。

## 为什么客户端不带令牌

源码仓库现在已公开，但零令牌设计保留：更新源只允许匿名只读，任何人都不需要把
个人访问令牌放进客户端。旧实现把 GitHub 访问令牌存在本地设置里，等于把一个长期有效、
能读私有仓库的凭据放进每个用户的机器；令牌输入框与 `updateToken` 字段已删除，
导出配置里也不再出现。

## 清单协议

```
{更新源根地址}/latest.json
{更新源根地址}/latest.json.sig      ← latest.json 原始字节的 Ed25519 签名（base64）
```

```json
{
  "version": "1.0.4",
  "published_at": "2026-11-07T10:36:04Z",
  "notes": "更新说明",
  "min_system": {
    "windows": "Windows 10 1809 及以上",
    "macos": "macOS 11 及以上",
    "linux": "glibc 2.31 及以上"
  },
  "assets": [
    {
      "platform": "windows",
      "arch": "x86_64",
      "name": "Fetchweir_1.0.4_x64-setup.exe",
      "url": "https://example.com/Fetchweir_1.0.4_x64-setup.exe",
      "size": 12345678,
      "sha256": "…"
    }
  ]
}
```

清单由 `node tools/New-FwManifest.mjs` 生成（只收录 `dist/` 里真实存在的安装包），
再由 `node tools/Sign-FwManifest.mjs --in latest.json --out latest.json.sig` 签名，
私钥从环境变量 `FW_SIGNING_KEY` 读取。两个文件与安装包一起挂到同一个仓库的 Release。

现在这两步由 `.github/workflows/release.yml` 在 tag 触发时自动执行，不再只靠手动发版。

**缺签名私钥时不会静默跳过**：流水线输出 `::warning title=发布未签名`，并在
step summary 里写明「本次不生成 latest.json / latest.json.sig，已安装的客户端不会
检测到这个版本」。这种发布只能手动下载安装包，自动更新链路对它是不可见的。

### 客户端校验顺序

1. 取 `latest.json` 与 `latest.json.sig`。
2. 用内置公钥验签：失败 → **直接中止**，不回退、不安装。
3. 版本按语义化规则比较（含预发布优先级，见 `src-tauri/src/update.rs` 单测）。
4. 预发布版本只在当前版本本身是预发布时才会被推荐。
5. 下载完成后校验 SHA256；不匹配 → 删除临时文件并拒绝安装。
6. 清单不存在时：
   - 默认 GitHub 源：回退到 Release 列表（`verified=false`，界面标注「未校验来源」，
     没有 SHA256 可校验）；
   - 显式指定的源（`FETCHWEIR_UPDATE_BASE`）：**不回退**，直接报「未找到可用的更新源」，
     避免拿另一个仓库的 Release 冒充这个源的结果。

## 更新源缺失时的实际表现

| 场景 | 状态 | 界面文案 |
| --- | --- | --- |
| 默认源，仓库不存在或私有 | `failed` | 未找到可用的更新源：{repo} 不存在或不可访问（客户端只读公开仓库，不携带任何令牌）… |
| 默认源，仓库存在但零 Release | `failed` | 未找到可用的更新源：{repo} 尚未发布任何版本 |
| 默认源有 Release 但没上传 `latest.json` | 回退 Release 列表 | 界面标注「未校验来源」，没有 SHA256 可校验 |
| `FETCHWEIR_UPDATE_BASE` 指向空目录/404 | `failed` | 未找到可用的更新源：更新源 {url} 没有提供 latest.json 清单 |
| 有清单、版本不高于当前 | `upToDate` | 已是最新版本（不展开详情面板） |
| 清单里没有当前平台/架构的资产 | `failed` | 更新清单中没有适用于当前平台与架构的安装包（v1.0.4 只有 Windows x64；该分支仅单测覆盖） |
| 清单签名被篡改 | `failed` | 清单签名校验失败：更新源内容可能被篡改或公钥不匹配 |

失败时详情面板不会展开，失败原因直接显示在「检查更新」按钮右侧的提示行，
不会出现只有一个「检查失败」而看不出原因的情况。

## 方案取舍

| 方案 | 做法 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| 公开主仓库 + 手动发 Release（当前） | 源码与产物同仓库；本地出包，`gh release create` 上传安装包与签名清单 | 零令牌、可镜像、可离线校验 | 发版仍需本机出包；非 Windows 平台要另找构建机 | **当前采用** |
| 单独公开产物仓库 | 私有源码 + 公开产物仓库 + 签名清单 | 源码与产物分离 | 源码仓库已公开，多一个仓库只增加运维 | 已废弃，更新源已并入主仓库 |
| 自建更新源 | 自己的 HTTPS 放 latest.json + 安装包 | 完全可控、可灰度 | 需要域名/服务器/证书与运维 | 支持（设置里改仓库或 `FETCHWEIR_UPDATE_BASE`），当前未部署 |
| 内置令牌 | 客户端带 PAT 读私有仓库 | 改动最小 | 令牌可被提取，等于把私有仓库读权限发给所有用户 | **排除** |

## 镜像

- 镜像只对 `https://github.com/...` 的资产链接有效（前缀转发）。
- 清单资产地址不是 github.com 时（自建源），下拉框自动禁用并显示
  「当前更新源为自建地址，镜像加速不可用」，不会留一个点了没反应的选项。

## 用户端如何收到更新

- 默认源指向公开主仓库的 latest Release；清单随 v1.0.4 上传后，1.0.4 用户可走
  「检查更新 → 验签 → 下载 → SHA256 校验」。
- **1.0.0 ~ 1.0.3 用户内置旧公钥**，对新私钥签的清单验签会失败，必须手动下载安装包。
- 有新版时显示版本号、发布说明、最低系统要求与「签名已校验」标记；
  「更新」= 下载 → 校验 → 安装 → 重启；「仅下载」= 落到系统下载目录。
- 非 Windows 平台当前没有资产，检查更新会提示「没有适用于当前平台与架构的安装包」。

## 发布密钥固定（不换钥）

客户端的信任锚点是编译进二进制的 `RELEASE_PUBKEY_B64`，与之配对的私钥只有一份：
本机 `.secrets/update-signing.pem`（已被 `.gitignore` 覆盖，不提交、不贴日志）。
签名私钥**不进 CI**，也不在任何流水线里生成。

约束（已落到脚本，不只写在文档里）：

- `tools/Sign-FwManifest.mjs` 签名前会用私钥推导公钥，与 `RELEASE_PUBKEY_B64` 比对；
  不一致直接以退出码 3 失败，并打印两把公钥与换钥流程，**不会生成或替换任何密钥**。
- `tools/New-FwSigningKey.mjs` 检测到已有私钥时默认拒绝执行，必须显式 `--force` 才会覆盖。

### 换钥（只在确实必须时）

顺序不可颠倒：

1. `node tools/New-FwSigningKey.mjs --force` 生成新密钥，把新公钥写入 `RELEASE_PUBKEY_B64`；
2. **先发布一个带新公钥的客户端版本**；
3. 等新版本铺开，再启用新私钥签的清单。

已发布的 **1.0.0 ~ 1.0.3** 客户端内置的是旧公钥，对新私钥签的清单验签必然失败，
更新检查会直接中止；这批用户只能按发布说明**手动下载安装包**升级。

## 已验证 / 未验证

已验证（本机）：

- 本地静态源全链路：检查更新 → 显示新版本 → 下载 → SHA256 一致 → 验签通过；
- 篡改清单任一字节 → 验签失败被拒，且不发起安装包下载；
- 清单签名有效但 `sha256` 字段错误 → 下载完成后校验失败、临时文件被删除；
- 无清单/空源 → `failed` + 「未找到可用的更新源」，界面提示行可见；
- 签名脚本换钥保护：固定私钥通过；临时私钥被拒（退出码 3）；
- 版本比较、按安装范围选包、自建源禁用镜像等 Rust 单测通过。

## 操作陷阱：替换已发布清单

- 用 `gh release upload --clobber` 替换 `latest.json` / `latest.json.sig` 后，GitHub 的
  `releases/latest/download/latest.json` 会短暂 404（旧 404 会被 CDN 缓存 1~2 分钟）。
  这一窗口内检查更新，客户端会按「源里没有清单」回退到 Release 列表模式：
  能发现新版本，但 `verified=false`、说明取 Release 正文。等缓存过期再查即恢复，不是签名问题。
- 替换清单必须同时重签 `.sig`（签名对整份字节生效），并且替换资产不会移动 tag；
  若只是改说明文案，可在改完后先本地验签，再等 1~2 分钟用旧客户端复验一遍。
