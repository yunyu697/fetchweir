# 浏览器扩展分发（当前口径与后续路径）

## 结论（v1.0.x）

**第一版只支持「加载已解压的扩展程序」这一条安装路径**，界面指引与「复制安装步骤」都按这条口径写。
另外三条路径（Edge 加载项商店、Firefox AMO 签名、`.crx` 企业策略）都还没有配置或验证，
下面把各自需要什么、卡在哪里写清楚，避免文档暗示「已经能装」。

| 路径 | 普通用户能否自己装 | 本版状态 | 主要阻断点 |
| --- | --- | --- | --- |
| 加载已解压目录 | 能（开发者模式，每台一次） | **唯一支持** | 需要打开开发者模式；浏览器重启后仍在 |
| Edge 加载项商店 | 能（商店页「获取」） | 未提交 | 需要 Partner Center 开发者账号、商店清单素材、隐私政策 URL 与审核 |
| Chrome 应用商店 | 能 | 不计划 | 同上，且需一次性开发者注册费；审核更严 |
| Firefox AMO unlisted 签名 | 能（装签名 `.xpi`） | 未签名 | 需要 AMO 账号与 API 凭据；每次发版重新签名 |
| `.crx` 站外安装 | **不能** | 不提供 | Chrome/Edge 正式版拦截（`CRX_REQUIRED_PROOF_MISSING`） |
| `.crx` 企业策略下发 | 仅受管设备 | 未验证 | 需要域/Intune 等管理端，个人设备用不了 |

## 本地打包：怎么做、要求是什么

```powershell
# 只出商店上传用的 zip（不需要私钥）
./tools/Build-FwExtension.ps1

# 同时出 CRX3（需要与 manifest key 配对的 RSA 私钥）
./tools/Build-FwExtension.ps1 -FwKeyPath D:\keys\fetchweir-extension.pem
```

脚本行为：

1. 打 `fetchweir-extension-<version>.zip`（清单在根目录，供商店上传）；
2. 用私钥推导扩展 ID，与 `src-tauri/src/nm.rs` 的 `EXTENSION_ID`
   和 `extension/manifest.json` 的 `key` 比对，不一致直接终止；
3. 调用本机 Chrome/Edge 的 `--pack-extension` 生成 CRX3（签名与 ZIP 封装由浏览器完成）；
4. 校验文件头 `Cr24` 与版本号 3，输出 `.crx`。

硬性要求：

- 私钥必须是 **PKCS#8 PEM 的 RSA 密钥**；PKCS#1（旧 `openssl genrsa` 默认格式）会被浏览器拒绝：
  `openssl pkcs8 -topk8 -nocrypt -in old.pem -out new.pem`；
- 私钥必须与 `manifest.json` 里的 `key` 配对。仓库里只有公钥（`key`），私钥不入库；
  若换私钥，扩展 ID 会变，必须同步改 `manifest.json` 的 `key` 与 `nm.rs` 的
  `EXTENSION_ID`，并重新构建应用，否则 Native Messaging 的 `allowed_origins` 授权失败。

### 实测记录（本机）

| 项目 | 结果 |
| --- | --- |
| 生成商店 zip | 23.1 KB |
| 生成 CRX3 | 24,476 字节，magic `Cr24`，版本 3 |
| 扩展 ID 校验 | 私钥推导值与预期一致时通过；不一致时脚本终止 |
| PKCS#1 私钥 | 浏览器报 “must be a valid format (PKCS#8…)” 并拒绝 |
| 未提供私钥 | 只出 zip，并打印密钥生成/转换说明 |

## Firefox 版本

Chrome 清单用 `background.service_worker` + `key`，Firefox 不支持 service worker 后台页、
也会忽略 key。`tools/Build-FwExtensionFirefox.ps1` 复制同一份业务代码并转换清单：

- `background.service_worker` → `background.scripts: ["background.js"]`（MV3 事件页）；
- 删除 `key`，改 `browser_specific_settings.gecko.id = "fetchweir@yunyu697"`
  （与 `src-tauri/src/nm.rs` 的 `FIREFOX_EXTENSION_ID` 一致）；
- `strict_min_version = 140.0`，并声明 `data_collection_permissions.required = ["none"]`。

产物：`dist/extension-firefox/`（可临时加载）与 `dist/fetchweir-extension-firefox.zip`。

实测（2026-11-08）：

- `npx web-ext lint --source-dir dist/extension-firefox`：**0 errors / 0 warnings / 0 notices**；
- Native Messaging 宿主已注册：
  `HKCU\Software\Mozilla\NativeMessagingHosts\dev.fetchweir.nmh` →
  `%APPDATA%\Fetchweir\nm\dev.fetchweir.nmh.firefox.json`，
  `allowed_extensions = ["fetchweir@yunyu697"]`。

未实测：在 Firefox 里真正加载扩展后与主程序的 Native Messaging 往返
（需要手动 `about:debugging` 临时加载；临时扩展重启浏览器后失效）。

临时加载步骤：Firefox → `about:debugging#/runtime/this-firefox` → 临时载入附加组件 →
选 `dist/extension-firefox/manifest.json`。

## Edge 加载项商店：需要的材料（未提交）

提交入口是 Microsoft Partner Center 的「Edge 加载项」发布流程，需要 Microsoft 账号并创建开发者身份。
材料清单：

| 类别 | 具体项 |
| --- | --- |
| 账号 | Microsoft 账号；Partner Center 开发者注册（需要真实联系人信息，公司/个人均可） |
| 包 | 商店版 zip（清单在根目录，用 `Build-FwExtension.ps1` 产出）；版本号必须递增 |
| 商店清单 | 名称、简短描述、详细描述、分类、支持语言、搜索关键词 |
| 素材 | 商店图标、至少一张商品截图（尺寸以 Partner Center 提交页为准，通常 1280×800 / 640×400） |
| 隐私 | 隐私政策 URL；「是否收集个人信息」声明 |
| 审核备注 | `nativeMessaging` 权限与 host 权限的用途说明、测试步骤、需要本地安装 Fetchweir 主程序的说明 |
| 发布 | 提交后审核，通过才会出现在加载项商店；更新走同一入口 |

阻断点（为什么本版不做）：

- 需要注册开发者账号并维护一份可公开访问的隐私政策页面，这是产品/合规动作，不是打包问题；
- `nativeMessaging` 属于高风险权限，审核会要求解释用途，且扩展在没有主程序时功能不完整，
  审核通过率与耗时不可控；
- 商店分发不改变扩展 ID（`manifest.json` 已内置 `key`），宿主 `allowed_origins` 无需改，
  但上架后的版本更新要跟着发版节奏走。

## Firefox AMO unlisted 签名：流程（未执行）

需要 AMO 账号与 API 凭据（addons.mozilla.org 开发者页生成 API key / secret），然后：

```powershell
npx web-ext sign --channel=unlisted `
  --api-key=$env:AMO_API_KEY --api-secret=$env:AMO_API_SECRET `
  --source-dir dist/extension-firefox --artifacts-dir dist
```

- `--channel=unlisted` 表示「只签名、不在 AMO 公开列表」，产物是签名后的 `.xpi`，
  用户拖进 Firefox 即可永久安装（不需要开发者模式）；
- unlisted 仍会过自动校验，必要时人工审核；压缩/混淆的代码需要同时提交源码；
- 每次发版必须重新签名，且 `version` 要递增；`gecko.id` 必须保持 `fetchweir@yunyu697`，
  否则 Native Messaging 的 `allowed_extensions` 不匹配；
- 签好的 `.xpi` 需要和 `latest.json`/安装包一起分发（或放到文档里的固定下载地址）。

阻断点：需要 Mozilla 账号与 API 凭据，并把「签名」接进发版流程；本版没有配置。

## `.crx` 企业策略下发：实际限制

- Chrome 从 33（Windows）/ 44（macOS）起禁止从本地路径或站外站点外部安装 CRX；
  Edge 同源限制。普通用户双击/拖入 `.crx` 会报 `CRX_REQUIRED_PROOF_MISSING`；
- 唯一可用的是**受管设备**上的企业策略：`ExtensionInstallForcelist` 或 `ExtensionSettings`
  指向 HTTPS 托管的 `update.xml` + CRX。设备必须加入域、Intune 或等同管理端，
  个人设备无法使用；
- Linux 上 Chrome 允许在 `/opt/google/chrome/extensions/*.json` 指定 `update_url`，
  属于系统级部署，同样不是普通用户的安装路径；
- 策略下发的扩展 ID 由 `manifest.json` 的 `key` 固定，与 Native Messaging 宿主
  `allowed_origins` 中的 ID 一致，无需额外改动；
- 本机没有域/管理端环境，因此**没有实测**策略下发。

## 分发组合与用户成本

| 方式 | 用户操作 | 是否需要审核 | 适用场景 | 成本 |
| --- | --- | --- | --- | --- |
| 解包目录加载（**当前唯一支持**） | 打开 `chrome://extensions` → 开发者模式 → 加载已解压 → 选 `extension/` | 否 | 内测、开发、企业内部分发 | 每台机器手动一次，重启浏览器仍在 |
| Edge 加载项商店 | 打开商店页 → 获取 | 是 | 面向普通用户 | Partner Center 账号 + 素材 + 审核 |
| Chrome 应用商店 | 同上 | 是 | 面向普通用户 | 开发者账号（一次性 $5）+ 审核 |
| Firefox 临时加载 / 签名 XPI | `about:debugging` 临时载入，或装 AMO unlisted 签名 `.xpi` | 临时加载不需要；`.xpi` 需签名 | Firefox 用户 | 已生成清单并通过 lint，签名流程未执行 |
| 企业策略 | 管理员用 `ExtensionSettings` / `ExtensionInstallForcelist` 下发 `.crx` 或更新源 | 否 | 托管设备、公司内网 | 需要域/管理端配置 |
| 自建更新源 | 首次仍需策略或开发者模式安装，之后自动更新 | 否 | 内测、企业 | 需要托管 `update_url` 与 CRX |
